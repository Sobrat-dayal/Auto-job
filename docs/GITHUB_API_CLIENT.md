# Stage 22: GitHub API Client & Rate Limit Governance

## 1. Client Architecture (`GitHubRestClient`)

The `GitHubRestClient` provides a resilient, asynchronous HTTP transport layer over `httpx.AsyncClient`. It is designed specifically to comply with GitHub REST API guidelines (API Version `2022-11-28`).

### 1.1 Standard Header Injection
Every outbound request automatically receives the following security and version headers:
- `Accept: application/vnd.github+json`
- `X-GitHub-Api-Version: 2022-11-28`
- `User-Agent: AUTONOM-Desktop-Assistant/1.0`
- `Authorization: Bearer <decrypted_token>` (when running in `PAT` mode)

### 1.2 Outbound Secret Sanitization
All exceptions, debug traces, and telemetry strings generated by the client pass through a token sanitizer. Any token pattern (`ghp_[A-Za-z0-9_]{36}`, `github_pat_[A-Za-z0-9_]{82}`) is automatically replaced with `[REDACTED_GITHUB_TOKEN]` before being logged or forwarded to the Supervisor.

## 2. Rate Limit Governance (`RateLimitController`)

GitHub enforces strict rate limits:
- **Unauthenticated**: 60 requests per hour (per IP).
- **Authenticated (PAT)**: 5,000 requests per hour (per user).
- **Search API**: 30 requests per minute.
- **Secondary Limits**: Triggered by concurrent requests or high request volumes within seconds.

```
Incoming Response Headers
  ├── x-ratelimit-limit: 5000
  ├── x-ratelimit-remaining: 4890
  ├── x-ratelimit-reset: 1731950000
  └── retry-after: (if throttled)
         │
         v
RateLimitController.record_headers()
  ├── remaining <= 5  --> is_rate_limited = True (Throttle active)
  ├── retry-after > 0 --> Set sleep backoff
  └── Notify Desktop Diagnostics Tab
```

### 2.1 Backoff Strategy
- **Soft Warning Threshold**: When `x-ratelimit-remaining` drops below 10% of total quota, the UI Diagnostics tab displays an amber indicator and background synchronization schedules are lengthened.
- **Hard Block Threshold**: If `remaining <= 2`, all non-critical background jobs are suspended until the Unix timestamp in `x-ratelimit-reset`.
- **Secondary Limit Handling**: If HTTP 403 or 429 is encountered with a `retry-after` header, the client enforces an asynchronous sleep (`asyncio.sleep(retry_after)`) and applies exponential jitter for subsequent attempts.

## 3. Conditional ETag Caching (`ETagCacheManager`)

To minimize API consumption, `ETagCacheManager` implements RFC 7232 HTTP conditional requests:
1. When a GET request succeeds (HTTP 200), the response body and its `ETag` header (e.g., `W/"64d43f0..."`) are stored in an in-memory cache keyed by request URL.
2. On subsequent queries to the same endpoint, the client adds `If-None-Match: <cached_etag>`.
3. If GitHub returns **HTTP 304 Not Modified**, the cached payload is returned instantly without consuming the user's hourly GitHub rate limit quota.
4. If HTTP 200 is returned, the cache entry and ETag are atomically updated.
